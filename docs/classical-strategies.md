`HedgingPolicy`. Независимый Python-эталон: `finmath.strategies.classical`.

## Единицы, наблюдения и общий путь исполнения

`moneyness = S/K`, `remaining_days / D = T`, `D=252` по умолчанию,
`sigma` — годовая историческая волатильность из общего наблюдения,
`N` — число акций в коротком call. Политика возвращает абсолютную целевую
позицию в **акциях**, не число заявок и не предполагаемое исполнение.

Python `CallObservation(moneyness, remaining_days, size_shares)` соответствует
Rust `CallObservation { moneyness, time_to_expiry, underlying_exposure: Short(N) }`.
Python не дублирует `as_of`: дату и отсутствие будущей информации обеспечивает
среда. Rust использует существующий `Observation` без изменения контракта.
Длинные call этой реализацией не поддержаны: Rust возвращает `EvaluationFailed`,
Python принимает только положительный размер короткой позиции.

Все три метода используют одни входы. Только Leland меняет используемую sigma,
только band учитывает фактический `shares_held` при выборе цели. Волатильность
и rolling window не оцениваются отдельно для каждой политики.
Годовая простая ставка funding переводится в непрерывную
`r = D*log1p(r_simple/D)`, как в #5; основной сценарий `r=0`.
Комиссия квантуется общим доменным правилом до 1e-9, как в бухгалтерии.

Цель передаётся в существующий `OrderLimits::hedge_order`, затем в общий
аукцион. Ограничения заявки и позиции, округление до лотов, контрагенты,
fees, funding, выдача call и settlement находятся вне политики. После
частичного исполнения следующее наблюдение содержит фактическую позицию.
Нельзя записать выданную цель в портфель как исполненную сделку.
Проверочный Rust-тест использует этот путь одинаково для каждого метода.

При отсутствии call или `remaining_days=0` цель равна нулю. Это инструкция
среде, а не обещание мгновенной ликвидации: применяются те же лимиты и fills.
Payoff рассчитывает бухгалтерия. Новая ротация call требует нового наблюдения.
При ошибке batch Rust возвращает `PolicyError`; вызывающий код должен отбросить
весь выходной buffer, который мог быть частично заполнен.

## BS delta и Leland

Для `T>0, sigma>0` цель BS равна `N*Phi(d1)`, где
`d1 = (log(S/K)+(r+sigma²/2)*T)/(sigma*sqrt(T))`.
Нулевая sigma использует детерминированный предел #5; в точке излома delta=0.5,
искусственного volatility floor нет. Общая цена выдачи call и его mark
остаются финансовыми правилами #5, а не ценой, выбранной отдельной стратегией.

В обозначениях нашего исполнения `c` — **односторонняя** доля traded notional:
покупка платит `c*|trade value|`, продажа тоже. Для ежедневного Leland:

```text
dt = 1/D
sigma_L² = sigma² + c*sigma*sqrt(8/(pi*dt))
         = sigma² + 2*c*sigma*sqrt(2/(pi*dt))
target = N*Phi(d1(sigma_L))
```

Это соответствует (5)–(7) Nguyen & Pergamenshchikov при постоянной ставке
и равномерном шаге. Если источник обозначает **round-trip** ставку как `k=2c`,
его множитель перед `sqrt(2/(pi*dt))` будет `k`, а не `c`.
Проверка коэффициента в наших единицах: ожидаемый turnover cost
`c*S²*Gamma*sigma*sqrt(2*dt/pi)` равен добавочному gamma-члену
`0.5*(sigma_L²-sigma²)*S²*Gamma*dt`.

При `sigma=0.2, c=0.001, D=252` получаем **sigma_L=0.21228850627100307**.
При `c=0` точно возвращается BS; при `sigma=0` поправка тоже нулевая.
Издержки здесь меняют цель; реальные fees всё равно списываются один раз
по фактическим fills. Поправка не создаёт дополнительного денежного перевода.

Большая sigma_L не означает большую delta для любого S/K: знак изменения
delta зависит от moneyness. Постоянная комиссия также не гарантирует точной
репликации при учащении торгов; это ограничение разобрано в §2.1 указанной
статьи. Для эндогенного ABM с дискретными лотами и partial fills Leland —
сравнительная стратегия, а не доказанно оптимальный хедж.

## Полоса бездействия

Для BS-центра `b=N*delta` и доли `w`:

```text
lower = max(0, b-w*N)
upper = min(N, b+w*N)
target = min(upper, max(lower, actual_shares_held))
```

Внутри полосы и на её границах позиция сохраняется. Снаружи цель — ближайшая
граница, поэтому стратегия не совершает лишний переход к центру.
`w=0` даёт BS. Общий диапазон целей короткого call — `[0,N]`, как в протоколе #1.
Это выбранный фиксированный benchmark; оптимальность такой симметричной
полосы, в отличие от оптимизируемых границ в Imaki et al., не утверждается.

## Конфигурация и выбор на validation

[`configs/classical-strategies.json`](../configs/classical-strategies.json)
содержит параметры BS/Leland/band. `band_width=0.05` — пример с явным статусом
`reference-defaults-not-validation-selected`, а не результат подбора.

Python:

```python
import json
from pathlib import Path
from finmath.strategies.classical import ClassicalPolicy, select_band_width

config = json.loads(Path("configs/classical-strategies.json").read_text())
policy = ClassicalPolicy(**config["policies"]["band"])
# pnls_by_width: {w: [net_pnl / (issue_spot * contract_size), ...]}
# Одни и те же validation episodes, один конкретный уровень c.
chosen_w = select_band_width(pnls_by_width, split="validation")
```

`select_band_width` требует полную сетку `{0,.01,.025,.05,.10,.20}`, конечные
значения, одинаковое ненулевое число episodes и `split="validation"`.
Минимизируется `log(mean(exp(-lambda*z)))/lambda`, `lambda=50`; вычисление
сдвинуто к худшему P&L для устойчивости. `z` — **normalized net P&L**,
не положительный shortfall. Равенство в пределах `1e-8` разрешается меньшим w.
Вызвать отдельно для каждой комиссии на тех же episodes, что используются
в #9/#16; запрещено выбирать по final-test или волатильности итогового рынка.

Проверка имени split сама не доказывает происхождение массива. Runner #16
обязан закрепить episode IDs и одинаковый порядок, dataset version/hash,
config/commit и сохранить выбранный w по c. Финальные test inputs не читались.
Полноценный подбор и заморозка параметров здесь не выполнялись: нужны принятые
release и loss из зависимых задач, затем #16/#17.

Rust принимает те же параметры через `ClassicalPolicy::new(method,
FundingRate, TradingDays)`: строки `bs/leland/band` соответствуют
`BlackScholes/Leland/Band { width: BandWidth::new(w)? }`.
Для CDF добавлен `libm` (та же зависимость, что в прототипе #14), версия
закреплена в Cargo.lock; Python использует стандартную библиотеку.

## Контрольные сценарии и оставшаяся интеграция

Общие [`tests/fixtures/classical-strategies.json`](../tests/fixtures/classical-strategies.json)
содержат 24 случая: ATM/OTM/ITM, разные размеры call, нулевые sigma/c,
положительный/отрицательный funding, D=252/360, полосу и expiry.
Ожидаемые числа получены прямыми скалярными формулами отдельно от реализаций.
Python и Rust сверяют цели с абсолютной точностью `1e-12` акции.
Rust затем проверяет общий лимит заявки в три лота и реальный fill в один лот;
для позиции внутри band заявка отсутствует. Python отдельно проверяет точные
границы, направление критерия риска, ties и запрет других split.

Пример: при `S/K=1, T=20/252, sigma=.2, N=100, c=.001` цели BS и Leland
равны соответственно `51.12374390690153` и `51.1927695955545` акции.
Band с `w=.05` сохраняет 50 акций; с нуля целится в `46.12374390690153`,
со 100 — в `56.12374390690153`. При общем лимите намерение может дать заявку
только на три акции, а имеющийся контрагент исполнит лишь одну.

До окончательной приёмки #10 требуется принятое #5. В #14 нужно использовать
этот модуль вместо прототипа `domain/classical.rs`, сохранить общий event order
и отдельно сверить pricing/funding в выдаче call и live marks с #5. Здесь
сохранён его публичный API, но приватные pricing helpers прототипа в модуль
стратегий не перенесены. Длинные рыночные прогоны и качество хеджирования
проверяются после интеграции; контрольные fixtures их не заменяют.
