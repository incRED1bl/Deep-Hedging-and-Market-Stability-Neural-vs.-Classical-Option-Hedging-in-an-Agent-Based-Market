# Как работаем

## Ветки и pull requests

1. Берём issue с ответственным, reviewer и DoD. Одна задача — один небольшой PR.
2. Создаём ветку от актуального `main`: `feat/14-market-integration`,
   `fix/8-option-settlement`, `docs/3-literature`, `test/5-bs-limits`
   или `chore/uv-update`. Для рефакторинга — `refactor/...`.
3. Рано открываем draft PR, если изменение затрагивает общий интерфейс.
   В описании указываем `Closes #N`, результат и способ проверки.
4. Перед review запускаем локальные проверки ниже. Для изменения поведения
   добавляем тест на содержательный сценарий или инвариант.
5. Снимаем draft и запрашиваем review у участника, указанного в issue.
   Нужен минимум **один Approve от другого участника**, зелёные `lint` и `test`,
   закрытые обсуждения. После новых коммитов review обновляется.
6. Мержим через **Squash and merge**, удаляем рабочую ветку. В `main` напрямую
   не пушим, защиту ради merge не отключаем. Issue закрывается после выполнения DoD.

Комментарии к коду и результатам обязательны, когда reviewer нашёл проблему;
сам по себе зелёный CI не подтверждает корректность финансовой модели.

## Ответственные и review

| Область / планируемый модуль | Автор | Основной reviewer |
| --- | --- | --- |
| `market/`, `agents/`, `accounting/` | Даня | Федя; Тим — интеграция стратегий |
| `strategies/classical/`, `metrics/` | Федя | Тим |
| `strategies/neural/`, `training/` | Тим | Федя |
| `data/`, калибровка | Лев | Федя; Тим — training dataset |
| `experiments/`, runner | Лев | Даня |
| Общие интерфейсы | Даня | Тим и Федя |
| CI, зависимости и правила репозитория | Тим | Другой участник с write-доступом |

Пути модулей относительны к `src/finmath/`; тесты повторяют эту структуру.
Автоматические запросы review задаёт `.github/CODEOWNERS`. Пока точные логины
Дани и Феди проверяются, в нём указаны подтверждённые `@incRED1bl` и
`@Levonidor`. Несколько owners одной строки означают выбор одного из них,
а не обязательное одобрение всех. Для проверки предметной части запрашиваем
конкретного reviewer из issue; после проверки логинов уточняем маршрутизацию.

## Python и зависимости

Используем Python из `.python-version` и uv **0.13.9**. Установка uv:
[официальная инструкция](https://docs.astral.sh/uv/getting-started/installation/).

```bash
uv python install
uv sync --locked
uv run ruff format .
uv run ruff check .
uv run pytest
```

Для новой runtime-зависимости: `uv add <package>`. Для инструментов:
`uv add --dev <package>`; для отдельного сценария — именованная dependency group.
Коммитим **и `pyproject.toml`, и `uv.lock`**. Обновляем только нужные зависимости,
причину обновления указываем в PR. CI ставит lockfile через `uv sync --locked`.

Kaggle CLI подключается явно: `uv sync --locked --group kaggle`. PyTorch и
GPU-зависимости добавляются вместе с задачей обучения в отдельную группу;
тяжёлое обучение в стандартный CI не входит.

## Один общий CI

Workflow `.github/workflows/ci.yml` запускается на PR и на push в `main`:

- `lint`: форматирование и Ruff;
- `test`: CPU-тесты через pytest, без внешних датасетов и credentials.

Каждый добавляет тесты своего модуля в этот pipeline. Отдельный workflow на
участника не нужен. Используем маленькие синтетические fixtures, фиксируем
seeds и проверяем финансовые инварианты, граничные случаи и интерфейсы.
Короткий smoke run симулятора добавляем, когда появится рабочий симулятор.
Прохождение текущего теста установки пакета не означает готовность модели.

GitHub Actions используют `contents: read`, actions закреплены на полный
commit SHA. Credentials Kaggle в Actions не нужны. Изменения `.github/`
проходят отдельное содержательное review вместе с остальным PR.

## Данные и эксперименты

Следуем [контракту данных и Kaggle](docs/data-and-kaggle.md). В Git храним код,
конфиги, небольшие синтетические fixtures и metadata с hashes. Исходные данные,
сгенерированные массивы, checkpoints, логи обучения и выгрузки Kaggle — вне Git.
`.env`, `kaggle.json`, API-токены и пароли не коммитим и не вставляем в PR.

Лев готовит воспроизводимый train/validation release; Тим подключает его к
обучению по зафиксированным version и SHA256. Финальные test seeds не участвуют
в выборе модели. В результатах сохраняем commit, config, seeds и версии данных.
Изменения гипотез, метрик, границ split и порядка событий отдельно описываем
в PR; уже полученные результаты не служат основанием переписать гипотезы.

Заимствованный код и AI-assisted фрагменты отмечаем у места использования;
даём источник и описываем, что проверили. Автор PR отвечает за результат.

## DoD для любого PR

- Задача и ожидаемое поведение описаны, пункты DoD issue выполнены.
- Тесты проверяют затронутое поведение; `lint` и `test` проходят.
- Интерфейсы, конфиги и инструкции обновлены, если изменились.
- Данные/веса воспроизводимы по metadata; secrets и большие файлы отсутствуют.
- Получен независимый review, замечания разобраны.
